# MCR Recording: Windows x86_64

Pre-made `.ct` recording from a Windows x86_64 machine for DAP integration testing.

## Recording details

- **Platform:** x86_64-pc-windows-msvc
- **Recording mode:** MCR, `--bootstrap stage0` (the Windows default): the
  recorder's stage-0 runtime (`ct_interpose_stage0.dll`) is mapped into the
  recorded process, so the recording carries that compiled DLL
- **Thread order:** global turns (`atomic_total_order`); every Windows
  recording carries them, and a strict replay enforces them
- **Tick source:** none
- **Program:** `ct_fixture_prog.exe` (compiled from `programs/ct_fixture_prog.c`)
- **Threads:** 4 (the main thread and 3 workers, one event stream each)
- **Format:** CTFS container version 5, `meta.dat` version 7
- **Embedded binaries:** none in `trace.ct`; the program in `trace-portable.ct`

## Files

| File | Description |
|------|-------------|
| `trace.ct` | Raw CTFS container with event streams, recorded via `ct-mcr record`. Does NOT contain embedded binaries. Used by emulator unit tests. Its `recording_id` is minted by the recorder. |
| `trace-portable.ct` | Portable export with the program embedded, created via `ct-mcr export --portable --recording-id 019e3a35-2545-7a00-8aaa-43ff20060002`. Used by browser GUI E2E tests. |
| `binaries/ct_fixture_prog.exe` | x86_64 PE executable compiled from `programs/ct_fixture_prog.c` with `/Od /Zi` (MSVC, no optimizations, debug info). |
| `source.c` | Symlink to `../../programs/ct_fixture_prog.c` (shared cross-platform source). |
| `regenerate.ps1` | Script to rebuild the binary, record the trace, and export the portable trace. |

## Publication rules

This repository is public. A Windows recording may carry the compiled
recorder DLLs (owner decision 2026-10-12), but never source code other than
the fixture program's own, and never personal data. A recording captures the
recording account's per-user state as well as its environment: the program's
DLLs read per-user registry values, and a recording made under a developer's
account captured `C:\Users\<user>\...\INetCache` that way. So the committed
traces are regenerated by the `windows-x86_64` job of
`.github/workflows/regen-device-recordings.yml`, on a self-hosted runner whose
service account names nobody, and that job refuses a recording that
`.github/scripts/ct_leak_scan.nim` finds personal data or source code in. Run
the same scan on any recording you make yourself before you commit it;
recorded under your own account, it will be refused.

## What the program does

1. **Pure computation:** `calculate_sum`, `sum_with_for`, `sum_with_while`.
2. **File I/O:** `CreateFileW`/`ReadFile`/`CloseHandle` on `NUL` generate
   file I/O events in the event stream.
3. **Multi-threading:** 3 worker threads (via `CreateThread`) each perform
   computation and I/O, producing per-thread event streams.

## How to regenerate

Dispatch the workflow (it uploads the recordings as an artifact; it commits
nothing):

```bash
gh workflow run regen-device-recordings.yml --ref <branch> -f platforms=windows-x86_64
```

The script itself, from the repository root in PowerShell, with `ct_mcr.exe`,
`ct_interpose.dll`, `ct_interpose_stage0.dll` (and its `.map`) and the
stage-0 stub (`stub.bin`, `stub_layout.txt`) built in
`../codetracer-native-recorder/ct_cli`:

```powershell
.\mcr\windows-x86_64\regenerate.ps1
```

It records under a cleared environment with a neutral `TEMP`. The raw trace
replays strictly only beside the sidecars `ct-mcr record` writes next to it
(`trace.ct.bootstrap_mode`, `trace.ct.stage0-runtime.dll` and `.map`), or with
a stage-0 runtime byte-identical to the one it was recorded with:

```powershell
ct_mcr.exe replay-worker --verify --replay-strict --bootstrap stage0 mcr\windows-x86_64\trace.ct
```

## Usage in tests

Used by DAP integration tests as a fixture for Windows x86_64 replay.

Tests can:
1. Load `trace.ct` directly for DAP inspection (metadata, events, registers).
2. Read the binary from `binaries/ct_fixture_prog.exe` and embed it into a copy of
   the trace to test binary-aware replay.
3. Verify that replay works both with and without the original binary present.
